# 天气助手 MCP 服务与聊天界面规格说明

## Problem Statement

用户希望通过一个中文聊天界面询问天气，但普通聊天模型无法可靠地知道实时天气，也不应该直接接触天气服务商凭据。项目需要验证一条完整链路：用户提出天气问题，DeepSeek 判断是否需要天气工具，聊天应用通过 MCP 调用独立天气服务，天气服务从和风天气获取并标准化天气事实，最后模型基于事实生成回答。

当前项目只有领域文档和架构决策，没有应用代码。第一阶段目标是本地可运行 POC，证明真实 MCP 调用、天气事实传递、会话地点记忆和前端流式聊天可以协同工作。

## Solution

构建一个全 TypeScript 的本地天气助手 POC，包含聊天应用和独立 Weather MCP 服务。

聊天应用提供浏览器聊天界面，并在后端连接 DeepSeek 和 Weather MCP 服务。DeepSeek 使用工具调用决定何时解析地点和查询天气；聊天后端负责执行 MCP 调用、把结构化天气事实回传给模型，并通过 SSE 向浏览器推送工具状态和回答文本。

Weather MCP 服务使用 Streamable HTTP 对外提供 MCP 能力，内部通过和风天气 GeoAPI、实时天气和每日预报接口获取数据。服务使用 JWT 和专属 API Host 认证和风天气，并将供应商响应转换为稳定的天气事实结构。浏览器永远不接触 DeepSeek 或和风天气凭据。

第一阶段只支持主动查询当前天气、未来每日预报和城市间天气比较。地点有歧义时必须先让用户选择；确认后的地点只在当前对话会话中保留，刷新页面后清空。

## User Stories

1. 作为一名用户，我希望询问某个明确地点的当前天气，以便知道该地点现在的天气情况。
2. 作为一名用户，我希望询问某个地点未来几天的每日天气预报，以便安排接下来的活动。
3. 作为一名用户，我希望比较两个地点同一天的天气事实，以便选择更适合出行的地点。
4. 作为一名用户，我希望使用自然的中文表达提问，而不必了解天气 API 或 MCP 的概念。
5. 作为一名用户，我希望询问“北京今天会下雨吗”时得到基于降水概率和天气现象的回答，而不是模型凭常识猜测。
6. 作为一名用户，我希望先询问“北京天气”，再询问“那明天呢”时，助手能够复用当前对话会话中的已确认地点。
7. 作为一名用户，我希望地点名称有歧义时，助手列出带有行政区和国家信息的候选地点，让我选择正确的地点。
8. 作为一名用户，我希望在没有提供地点时，助手向我追问地点，而不是默认猜测我的位置。
9. 作为一名用户，我希望授权浏览器定位后，能够使用当前位置查询天气。
10. 作为一名用户，我希望拒绝浏览器定位后，仍然可以通过输入城市名称查询天气。
11. 作为一名用户，我希望查询结果标明地点、数据时间和时间区，以便判断回答是否适用于我。
12. 作为一名用户，我希望看到“正在解析地点”“正在查询天气”等简短状态，以便知道助手没有卡住。
13. 作为一名用户，我希望回答以流式方式显示，以便较早看到正在生成的内容。
14. 作为一名用户，我希望模型只基于天气服务返回的天气事实回答，不把模型猜测说成实时天气。
15. 作为一名用户，我希望天气服务失败、超时或返回不完整数据时，助手明确告诉我无法确认，而不是编造结果。
16. 作为一名用户，我希望刷新浏览器后当前地点被清空，以便不同使用场景不会意外复用上一次地点。
17. 作为一名用户，我希望第一版界面只关注聊天和天气结果，不需要注册账号或管理历史记录。
18. 作为一名开发者，我希望 Weather MCP 服务独立于聊天应用运行，以便验证聊天应用确实通过 MCP 调用了天气工具。
19. 作为一名开发者，我希望模型看到的是稳定的工具描述和 JSON Schema，而不是和风天气供应商的原始响应格式。
20. 作为一名开发者，我希望天气工具能够解析城市名称、返回当前天气并返回每日预报，以便覆盖第一版核心对话。
21. 作为一名开发者，我希望地点解析在天气查询前完成，以便天气工具只接收已确认地点的坐标和时区。
22. 作为一名开发者，我希望聊天应用不直接调用和风天气，以便供应商凭据和供应商耦合都留在 Weather MCP 服务内。
23. 作为一名开发者，我希望替换天气数据源时不需要修改聊天界面或模型提示，以便保留 MCP 边界的可替换性。
24. 作为一名开发者，我希望替换 LLM 供应商时不需要修改 Weather MCP 服务，以便天气领域能力保持独立。
25. 作为一名开发者，我希望工具参数在执行前被后端校验，以便模型生成的非法 JSON 或未知地点不会直接进入外部 API。
26. 作为一名开发者，我希望聊天后端把工具开始、工具完成、文本增量和最终完成事件推送给前端，以便界面保持清晰的运行状态。
27. 作为一名开发者，我希望当前会话的已确认地点以结构化状态保存，以便后续问题不依赖模型从历史文本中猜地点。
28. 作为一名开发者，我希望天气事实包含来源、时间、地点和单位，以便模型能够正确解释数值并生成可核验的回答。
29. 作为一名开发者，我希望 API 密钥只通过后端环境变量提供，以便浏览器和前端资源不会泄露凭据。
30. 作为一名开发者，我希望 POC 可以在本机启动聊天应用和 Weather MCP 服务，以便不依赖生产基础设施验证完整链路。
31. 作为一名测试人员，我希望通过一次浏览器聊天流程验证完整用户行为，而不是只验证内部函数返回值。
32. 作为一名测试人员，我希望使用确定性的 DeepSeek 和和风天气替身测试正常、歧义和失败场景，以便测试不依赖外部服务的实时结果。
33. 作为一名维护者，我希望日志记录请求 ID、工具名、耗时和成功失败状态，以便定位 MCP 调用链问题。
34. 作为一名维护者，我希望日志不包含 DeepSeek 密钥、和风天气凭据或完整用户对话，以便降低敏感信息泄露风险。

## Implementation Decisions

- 使用全 TypeScript 实现聊天应用和 Weather MCP 服务，聊天应用使用 Next.js。
- 一个仓库包含两个应用：面向用户的聊天应用和独立运行的 Weather MCP 服务。暂不抽取共享包，除非出现真实的跨应用类型复用需求。
- 聊天应用的后端同时承担 DeepSeek 客户端和 MCP 客户端职责；浏览器只连接聊天应用。
- 使用 DeepSeek Chat Completions API、`deepseek-flash`、流式输出和工具调用。第一版关闭 thinking mode，以减少工具调用状态处理复杂度。
- DeepSeek 的工具调用参数必须经过后端 JSON Schema 校验；校验失败时不得调用天气服务。
- Weather MCP 使用 Streamable HTTP；第一版不实现旧版 SSE，也不要求 stdio 集成。
- Weather MCP 第一版提供三个工具：地点解析、当前天气、每日天气预报。
- 地点解析接收用户输入，返回标准地点候选；候选包含名称、行政区、国家、经纬度和时区。
- 只有用户明确选择或授权使用的地点才成为已确认地点。存在多个候选时，在确认之前不得调用天气工具。
- 当前天气工具和每日预报工具只接收已确认地点的标准坐标、时区和查询范围，不重新解释自然语言地点。
- 每日预报默认返回未来 7 天，使用查询地点的本地日期和时间。
- 第一版不暴露小时预报、天气预警、空气质量和生活指数工具。
- Weather MCP 内部使用和风天气 GeoAPI、实时天气和每日预报能力；和风天气认证使用 JWT 和开发者专属 API Host。
- Weather MCP 将和风天气响应转换为结构化天气事实，至少包含地点、坐标、时区、数据时间、温度、体感温度、天气现象、降水概率、降水量、风向、风速和来源。
- 结构化天气事实由 Weather MCP 返回，面向用户的自然语言表达由 DeepSeek 生成。
- 聊天应用通过 SSE 向浏览器推送工具开始、工具完成、文本增量、消息完成和错误事件。
- 当前会话只在内存中保存已确认地点和对话历史；刷新页面后清空，不使用数据库。
- API 凭据只存在后端环境变量中，浏览器不得接收 DeepSeek 或和风天气凭据。
- POC 只面向本机运行，不增加用户认证、账号系统、持久化、限流或公网部署配置。
- 所有外部 API 错误转换为稳定的内部错误类别；向用户返回可理解的失败说明，向日志记录请求 ID、工具名、耗时和错误类别。
- 测试采用一个最高层浏览器聊天 seam：真实运行 Weather MCP，DeepSeek 和和风天气使用确定性测试替身，验证用户可见行为和 MCP 调用链。

## Testing Decisions

- 测试只验证用户可观察的行为：输入问题、界面状态、工具状态、最终中文答案、追问和失败反馈；不测试内部函数调用次数或具体实现类名。
- 最高层测试从浏览器聊天界面开始，贯穿聊天后端、DeepSeek 工具调用适配、真实 Weather MCP 和测试替身天气数据源。
- 正常天气查询测试：用户询问明确地点的当前天气，界面显示地点解析和天气查询状态，最终答案包含测试数据中的天气事实。
- 每日预报测试：用户询问未来三天预报，回答使用每日预报事实和地点本地日期。
- 连续追问测试：用户先确认地点，再使用“那明天呢”等省略地点的表达，系统复用已确认地点。
- 地点歧义测试：地点解析返回多个候选，系统显示候选并暂停天气查询；用户选择后才继续。
- 缺少地点测试：用户提出没有地点的天气问题，系统追问地点，不调用天气查询工具。
- 位置授权测试：允许浏览器定位时可以使用坐标查询；拒绝授权时可以回退到城市名称输入。
- MCP 失败测试：Weather MCP 不可用或工具失败时，界面显示明确错误，不输出伪造天气。
- 数据源失败测试：和风天气替身返回超时、认证失败或不完整数据时，系统返回稳定失败类别并结束流式响应。
- 非天气问题测试：用户提出与天气无关的问题时，模型不调用天气工具，仍能正常结束对话。
- 安全测试：浏览器网络响应和普通日志中都不出现 DeepSeek 或和风天气凭据。
- 目前代码库没有可复用的测试先例；第一条测试建立浏览器端到端测试基础，后续测试沿用同一 seam。

## Out of Scope

- 用户注册、登录、账号管理和权限系统。
- 对话历史持久化、跨设备同步和数据导出。
- 天气订阅、定时播报、主动推送和通知中心。
- 公网部署、横向扩展、负载均衡和生产级监控。
- 小时预报、分钟级降水、天气预警、空气质量、生活指数、台风和历史天气。
- 多天气数据源聚合、数据源自动切换和数据源比较。
- 让 LLM 直接调用和风天气或其他供应商 API。
- 让浏览器直接连接 Weather MCP 服务。
- 完整的天气地图、图表、天气图标资源和复杂可视化。
- 个性化穿衣模型、医疗建议、灾害应急决策和高风险出行决策。
- 多语言界面和用户自定义单位设置。
- MCP Registry 发布、OAuth 认证和多租户隔离。
- 旧版 MCP SSE 和本地 stdio 传输适配。

## Further Notes

- 运行 POC 前需要准备 DeepSeek API Key、和风天气 JWT 凭据和开发者专属 API Host；这些值只通过后端环境变量提供。
- 和风天气官方文档提供 GeoAPI、实时天气和每日天气预报能力；每日预报默认最多可请求 10 天，本规格将产品默认限制为 7 天。
- 该规格遵循 `docs/adr/0001-separate-weather-facts-from-conversation.md` 中已确认的 MCP 边界。
- 规格已准备使用 triage 角色 `ready-for-agent`；本仓库实际对应的 GitHub 标签名称是 `可交给代理`。
